## 2026-05-09 — Phase 1: `LATEST` resolves to AF4 recipe artifact

- Context: Phase 1 (openrewrite, Path B). Initial run with `recipeArtifactCoordinates=org.axonframework:axon-migration:LATEST`.
- Surprise: Maven resolved `LATEST` to the locally cached `axon-migration:4.13.1` (the AF4 line of the same artifact id), not the AF5 5.x line. Combined with `rewrite-maven-plugin:6.39.0`, this caused a bytecode `VerifyError` (`Type 'UsesType' is not assignable to 'JavaVisitor'`) before any rewrites ran. Spring milestones repo also returned 401 for non-authenticated metadata fetches, which made `LATEST` unable to discover AF5 versions over the wire.
- Resolution: pinned to explicit `5.1.1-SNAPSHOT` per recipe doc — fall-back path. `5.1.0` also failed because the `pom` is gated behind the auth-required `spring-milestones` repo. `5.1.1-SNAPSHOT` resolved successfully via `central.sonatype.com/repository/maven-snapshots/`.
- Takeaway for future runs in this project: always pass an explicit recipe version (recommend `5.1.1-SNAPSHOT` until a fully published 5.x release lands in unauthenticated central). `LATEST` is unsafe here.

## 2026-05-09 — Phase 1: OpenRewrite went past "mechanical" — already produced correct AF5 shape for `CREATE_IF_MISSING`

- Context: Phase 1 (openrewrite, Path B) rewrote `Army`, `Astrologers`, `Calendar`, `Dwelling` to AF5 `@EventSourced(tagKey, idType)`.
- Initial impression (incorrect): "the recipe removed `@CreationPolicy(CREATE_IF_MISSING)` without an AF5 equivalent — behaviour is now lost".
- Correction (verified on Army during Phase 2): the recipe DID produce the AF5 equivalent. Per [aggregate/creation-policy-decision.md](../.claude/skills/axon4-to-axon5-migration/references/aggregate/creation-policy-decision.md), the AF5 shape for `CREATE_IF_MISSING` is "**instance** `@CommandHandler` (NOT static) + no-arg `@EntityCreator`". OpenRewrite produced exactly that:
  - Command handlers stayed instance (not made static).
  - A no-arg constructor annotated `@EntityCreator` was added to the aggregate.
  - `apply(...)` was rewritten to `eventAppender.append(...)`.
  - The `RemoveCreatureFromArmyTest.givenEmptyArmy_...` expectation needed updating: AF4 would throw `AggregateNotFoundException` for a missing aggregate, but AF5 with no-arg `@EntityCreator` materialises an empty entity and runs the instance handler — so the domain rule (`Can remove only present creatures`) fires instead. This is the documented gotcha in the decision-matrix doc.
- Stranded comment: the source still says `// performance downside in comparison to constructor` — was a note about `CREATE_IF_MISSING`'s performance cost on EVERY command. Still loosely accurate (instance handler still re-loads the aggregate) but the original referent is gone. Left in place; can be cleaned up during stabilization.
- Implication: each per-aggregate Phase 2 step is mostly **verification**, not heavy rewriting — confirm the entity-creator pattern matches what AF4's `CreationPolicy` value implied, fix any test expectations that asserted on AF4-only exceptions, and verify scoped tests pass. See Army (commit pending) as the canonical example.
- See: phase-1 commit `1911b46`, phase-2-Army commit `8bf3deb`.

## 2026-05-09 — Phase 2 / Dwelling: NPE-on-null-state fix via explicit domain guard

- Context: Phase 2 / Dwelling. `RecruitCreatureTest.givenNotBuiltDwellingWhenRecruitCreatureThenException` fed an empty event stream, then sent `RecruitCreature`.
- Surprise: AF4 threw `AggregateNotFoundException` (the test author commented "exception is not from domain, AggregateNotFoundException is meaningless"). AF5 with no-arg `@EntityCreator` materialises an empty Dwelling instead — `dwellingId`, `creatureId`, `availableCreatures` are all `null`. The first rule constructed in `decide(RecruitCreature, EventAppender)` is `RecruitCreaturesNotExceedAvailableCreatures(creatureId, availableCreatures, ...)`, whose `isViolated()` calls `dwellingCreatureId.equals(...)` — NPE on null `dwellingCreatureId` (the `creatureId` field of the empty Dwelling), not a domain exception.
- Resolution: per [creation-policy-decision.md](../.claude/skills/axon4-to-axon5-migration/references/aggregate/creation-policy-decision.md) "NPE on null state", added an explicit domain-level guard at the top of the recruit handler:
  ```java
  new OnlyBuiltDwellingCanHaveAvailableCreatures(dwellingId).verify();
  ```
  This reuses the existing rule already used by `IncreaseAvailableCreatures`. Message ("Only built dwelling can have available creatures") is slightly broader than "Only built dwelling can recruit creatures" but matches the actual condition (`dwellingId == null`). Test expectation updated to match. Net effect: AF4's meaningless `AggregateNotFoundException` becomes a clear domain rule violation — improvement, not just preservation.
- Same `IncreaseAvailableCreaturesTest.givenNotBuildDwellingWhenIncreaseAvailableCreaturesThenException` was already covered by the existing `OnlyBuiltDwellingCanHaveAvailableCreatures(dwellingId).verify()` call at the top of the increase handler — only the test expectation needed updating.
- See: phase-2-Dwelling commit (this commit).

## 2026-05-09 — Phase 3 / WhenWeekSymbolProclaimed: AF5 `Message` is NOT generic

- Context: Phase 3 / event-processor item 5 — loop-dispatch handler. Per recipe Step 6 "Loop / multiple dispatches → `CompletableFuture.allOf(...)`". Helper method type signature initially set to `CompletableFuture<? extends Message<?>>` per recipe wording.
- Surprise: compile error "The type Message is not generic; it cannot be parameterized with arguments <?>". Verified by `javap` against `axon-messaging-5.1.1-SNAPSHOT.jar`: `org.axonframework.messaging.core.Message` is declared as `public interface Message` (no type parameter). The recipe's pseudocode (`commandResult.getResultMessage()` returns `CompletableFuture<? extends Message>`) is correct; only the documentation hint "`CompletableFuture<? extends Message<?>>`" was misleading.
- Resolution: changed helper return type to `CompletableFuture<? extends Message>` (no `<?>`). Rest of the loop-pattern compiles cleanly: `repository.findAllByGameId(...).stream().filter(...).map(d -> helper(dispatcher, d, ...)).toArray(CompletableFuture[]::new)` → `CompletableFuture.allOf(futures)`.
- Future-proofing for this skill: recipe `event-processor.md` should be tightened to use `CompletableFuture<? extends Message>` (without `<?>`) in any documented pseudocode.
- See: phase-3-WhenWeekSymbolProclaimedThenIncreaseDwellingAvailableCreatures commit (this commit).

## 2026-05-09 — Phase 7 / StreamProcessorsOperations: AF5 `TokenStore` API forces `progressOf` deferral

- Context: Phase 7 / read-configuration item 1. The class injected both `EventProcessingConfiguration` and `TokenStore` (AF4 shape — diagnostic helper that read segment positions to compute replay progress).
- Surprise: AF5 `org.axonframework.messaging.eventhandling.processing.streaming.token.store.TokenStore` rewrites every operation as `CompletableFuture<...>` AND requires a `ProcessingContext` parameter on every method (`fetchSegments(String, ProcessingContext)`, `fetchToken(String, int, ProcessingContext)`, …). There is no public "no-context" or default `ProcessingContext` instance for diagnostic callers running outside a unit-of-work — the read-configuration recipe explicitly says to drop the redundant `TokenStore` field, but the recipe does not address callers that *use* `fetchSegments` / `fetchToken` directly.
- Resolution: migrated `reset(...)` per recipe (switched field to `AxonConfiguration`, looked up `StreamingEventProcessor` via `getModuleConfiguration("EventProcessor[" + name + "]").flatMap(m -> m.getOptionalComponent(StreamingEventProcessor.class))`, replaced `shutDown()` / `resetTokens()` / `start()` with `.orTimeout(30, SECONDS).join()`-bridged async calls). Stubbed `progressOf(...)` body to throw `UnsupportedOperationException` with a `TODO #LLM` comment pointing at `StreamingEventProcessor.processingStatus()` (per-segment `EventTrackerStatus` map, returned synchronously) as the AF5-native replacement. `progressOf` is unused outside this file and `Progress` record is preserved verbatim — admin path can be revived in stabilization.
- Takeaway: the recipe step 6 "drop redundant `TokenStore` field" only fits classes whose use of `TokenStore` is the AF4 implicit "looked up by name" pattern. Direct diagnostic readers of `fetchSegments` / `fetchToken` need a per-callsite redesign; flag them instead of attempting an automated port.
- See: phase-7-StreamProcessorsOperations commit (this commit).

## 2026-05-09 — Phase 9 / event-storage-engine: no bean swap needed; deliverable is SQL only

Path A — code unchanged.
- Resolution:
  - **Path picked: A — JPA via auto-config.** No `@Bean EventStorageEngine` exists in the project, so there is nothing to delete and nothing to add. Auto-config wins.
  - Path A.2 (custom enhancer) skipped — AF4 did not tune `batchSize` / `gapTimeout` / `persistenceExceptionResolver`.
  - Path A.3 (custom `Serializer` → `Converter`) — `SerializationConfiguration` declares Jackson `Module` beans (NOT custom `org.axonframework.serialization.Serializer` subclasses); these are picked up by Spring's `ObjectMapper` autoconfig and remain valid under AF5's Jackson-backed `Converter`. No serializer ports flagged. B4 does not fire.
  - Path A.4 (schema migration) — emitted `01-rename-domain-to-aggregate-event-entry.sql` under `.axon4-to-axon5-migration/sql/`, PostgreSQL-flavoured. Renames `domain_event_entry` → `aggregate_event_entry`, renames all 7 columns, tightens nullability on `version` / `aggregate_sequence_number` / `identifier`, drops `NOT NULL` on `aggregate_identifier` (DCB-friendly), creates the `aggregate-event-global-index-sequence` and seeds it past the current max `global_index`, and adds the unique `(aggregate_identifier, aggregate_sequence_number)` index. **NOT executed by the orchestrator** — user runs out-of-band on a non-prod copy first, verifying row counts before/after. No Flyway directory exists in this project, so the SQL lives under the skill's state dir; user can move it into a Flyway changeset if desired.
  - Path A.5 (entity scan) — no explicit `LocalContainerEntityManagerFactoryBean` / `packagesToScan` / `@EntityScan` in the project; Spring Boot's default entity scan plus AF5's `@RegisterDefaultEntities` will pick up `org.axonframework.eventsourcing.eventstore.jpa.AggregateEventEntry` from the framework JAR. No code change required.

## 2026-05-09 — Phase 9 / event-storage-engine: "auto-config wins" claim was WRONG; needs explicit `@Bean`

- Context: After committing the no-bean-swap variant of Phase 9 (commit `ec5b2a8`), the user pushed back: "are you sure? I'm almost sure it will register non-aggregate-based version???" The user was right.
- Surprise: the recipe doc's Path A.1 claim — "AF5 `JpaEventStoreAutoConfiguration` registers `AggregateBasedJpaEventStorageEngine` automatically when an `EntityManagerFactory` and `PlatformTransactionManager` are present and no other `EventStorageEngine`/`EventStore` bean exists" — is technically true in isolation, but **does not survive contact with `axoniq-spring-boot-starter`** (the commercial starter Phase 1 swapped to). Verified by inspecting bytecode in `~/.m2/repository`:
  - `axoniq-spring-boot-starter:5.1.1-SNAPSHOT` transitively pulls `io.axoniq.framework:axon-server-connector` onto the classpath. That JAR ships a ServiceLoader-discovered `io.axoniq.framework.axonserver.connector.configuration.AxonServerConfigurationEnhancer` whose `enhance()` method calls `registry.registerIfNotPresent(eventStorageEngineDefinition(), SearchScope.ALL)` — and `eventStorageEngineDefinition()` builds via `AxonServerEventStorageEngineFactory.constructForContext(...)`, i.e. **`AxonServerEventStorageEngine` (DCB-flat), NOT aggregate-based**.
  - `AxonServerConfigurationEnhancer.order() = Integer.MIN_VALUE + 10` (= -2147483638) — runs as early as ConfigurationEnhancers can run.
  - `JpaEventStoreAutoConfiguration$AggregateBasedJpaEventStorageEngineConfigurationEnhancer.order() = Integer.MAX_VALUE - 600` (= 2147483047) — runs as late as ConfigurationEnhancers can run.
  - Result: connector enhancer wins the `registerIfNotPresent` race by ~4 billion in ordering. The JPA enhancer's later `registerIfNotPresent(EventStorageEngine, …, SearchScope.ALL)` finds the slot occupied and skips. **DCB-flat AxonServer engine ends up registered, against an `axon-server-connector` connection that doesn't exist** (because `axon.axonserver.enabled: false` in `application.yaml` keeps `AxonServerAutoConfiguration`'s `@ConditionalOnProperty(matchIfMissing=true)` connection beans dormant).
  - The `axon.axonserver.enabled: false` flag does **NOT** disable the connector's ServiceLoader enhancer — it only gates the Spring `@Bean` methods inside `AxonServerAutoConfiguration` (connection manager, configuration object, etc.). The ServiceLoader enhancer is independent of Spring conditions and runs whenever the connector JAR is on the classpath.
- Resolution: declare an explicit Spring `@Bean EventStorageEngine` returning `new AggregateBasedJpaEventStorageEngine(new JpaTransactionalExecutorProvider(emf), eventConverter, UnaryOperator.identity())`. The mechanism that makes this work is in `org.axonframework.extension.spring.config.SpringComponentRegistry.hasComponent(Class, String, SearchScope)`:
  ```java
  return switch (searchScope) {
      case ALL -> components.contains(...) || contextHasComponent(type, name);  // <— BOTH
      …
  };
  ```
  With `SearchScope.ALL` (which is what BOTH the connector enhancer and the JPA enhancer use), `hasComponent` checks the Spring `BeanFactory` (`beanFactory.getBeanNamesForType(type).length > 0`) in addition to the local `Components` map. The Spring `@Bean` is visible via that path BEFORE either enhancer runs. Both `registerIfNotPresent` calls see the slot already occupied and skip. Net result: `AggregateBasedJpaEventStorageEngine` is the registered `EventStorageEngine`, regardless of enhancer ordering. New file: `com.dddheroes.heroesofddd.shared.infrastructure.EventStoreConfiguration`.
- Takeaway for the recipe (and any future AF5 migration where the project keeps a non-AS storage backend on `axoniq-spring-boot-starter`): **never rely on JPA auto-config alone** — always declare an explicit `@Bean EventStorageEngine` for the desired implementation. The recipe's existing Path B-aggregate.1 already documents this pattern for Axon Server (explicit `@Bean` to override the connector's DCB-flat default); the same pattern applies to Path A whenever the connector JAR is on the classpath. The commercial starter's coordinate swap (Phase 1 OpenRewrite) is silently sufficient to put the connector on the classpath, even when the project has zero intent to use Axon Server.
- Side note: AF5 base `EventSourcingConfigurationDefaults` (registered via ServiceLoader from `axon-eventsourcing`) provides `InMemoryEventStorageEngine` as the default `EventStorageEngine`. In a non-Spring, no-`axon-server-connector` setup, that's what would win. Spring auto-config + connector flips this entirely — the explicit `@Bean` is the only deterministic answer.
- See: phase-9-event-storage-engine fix-up commit (this commit). Pinned-decisions in `progress.md` updated from `A — JPA via auto-config` → `A — JPA via explicit @Bean EventStorageEngine`.

## 2026-05-12 — Phase 9 follow-up: explicit `@Bean EventStorageEngine` silently disables `@RegisterDefaultEntities`

- Context: after the Phase 9 fix-up (commit `77d5ea3`) wired an explicit `@Bean EventStorageEngine` in `EventStoreConfiguration`, reactivating the `@SpringBootTest` read-model suite (`GetDwellingByIdTest` etc., test refactor in commit `1228b5b`) revealed three context-load failures in sequence: `Could not resolve root entity 'AggregateEventEntry'`, then `… 'TokenEntry'`, then a `relation "idx_game_id" already exists` Postgres error from duplicate `@Index(name="idx_game_id")` on two read-model entities. The initial-looking JUnit error was an even more misleading `No ParameterResolver registered for parameter [...AggregateEventPublisher...]` on the test constructor, which is a separate Spring TestContext issue (see resolution below).
- Surprise: AF5 ships a mechanism that is *meant* to make framework JPA entities discoverable without user `@EntityScan`. `JpaEventStoreAutoConfiguration` (AF5 `extensions/spring/spring-boot-autoconfigure`) carries `@RegisterDefaultEntities(packages = {"org.axonframework.eventsourcing.eventstore.jpa"})` (analogous to AF4's `@RegisterDefaultEntities`), which `@Import`s `DefaultEntityRegistrar` to append the package to Spring Boot's `AutoConfigurationPackages`. `JpaAutoConfiguration` does the same for `…token.store.jpa`; AxoniqFramework's `JpaDeadLetterQueueAutoConfiguration` does the same for `io.axoniq.framework.messaging.eventhandling.deadletter.jpa`. **None of those mechanisms fired in this project.** Verified by reading the AF5 autoconfig sources: `JpaEventStoreAutoConfiguration` is annotated `@ConditionalOnMissingBean(value = {EventStore.class, EventStorageEngine.class})`. Spring evaluates class-level `@Conditional` BEFORE processing `@Import`, so the Phase 9 `@Bean EventStorageEngine` we were forced to declare (commit `77d5ea3`) skips the entire autoconfig class — and with it, the `DefaultEntityRegistrar` that would have appended `org.axonframework.eventsourcing.eventstore.jpa` to `AutoConfigurationPackages`. The `JpaAutoConfiguration` (TokenEntry) side then collapsed for a different reason: once we added a user-side `@EntityScan` to fix `AggregateEventEntry`, Spring Boot's `JpaBaseConfiguration.getPackagesToScan()` uses `EntityScanPackages` *instead of* `AutoConfigurationPackages`, so the still-active `@RegisterDefaultEntities` for the token-store package stopped being read. The two failures are linked: fixing one with `@EntityScan` invalidates the framework's mechanism for the other.
- Resolution (commit `d3319d9`): user-side workaround in this project.
  - `HeroesOfDDDApplication` gained `@EntityScan(basePackages = {"com.dddheroes.heroesofddd", "org.axonframework", "io.axoniq.framework"})` — covers `AggregateEventEntry`, `TokenEntry`, and `DeadLetterEntry` in one annotation, future-proofed against new framework JPA entities being added under either group.
  - `src/test/resources/spring.properties` added with `spring.test.constructor.autowire.mode=all` so `SpringExtension` autowires constructor parameters on the new `AggregateEventPublisher`-based test base classes (default `@TestConstructor` mode is `ANNOTATED`, which surfaced as the misleading "No ParameterResolver registered" error before context loading even ran).
  - Renamed duplicate `@Index(name = "idx_game_id")` on `DwellingReadModel` and `BuiltDwellingReadModel` to per-table names (`idx_read_model_dwelling_game_id`, `idx_read_model_built_dwelling_game_id`). Pre-existing schema collision that `ddl-auto: update` on a long-lived Postgres had been hiding; a fresh Testcontainers DB exposes it on every boot.
- Why NOT a framework-side PR yet: three shapes were considered against `JpaEventStoreAutoConfiguration` —
  - (A) split: move `@RegisterDefaultEntities` to a new always-loaded `JpaEventStoreEntitiesAutoConfiguration` gated only by `@ConditionalOnClass(EntityManagerFactory.class)`; bean wiring keeps its `@ConditionalOnMissingBean`.
  - (B) merge: append `eventsourcing.eventstore.jpa` to `JpaAutoConfiguration`'s existing `@RegisterDefaultEntities`.
  - (C) loosen: drop the class-level `@ConditionalOnMissingBean` and keep it only on the `@Bean` method.

  All three eagerly register `AggregateEventEntry` for users who DON'T use JPA event storage — e.g. an Axon Server deployment where the entity table is pure schema pollution. The framework's current coupling ("register entities only when JPA engine wins the autoconfig") is plausibly *intentional*, gated by `@ConditionalOnMissingBean` to mean "register entities only when this autoconfig is going to provide the engine". Phase 9 violates that intent by always providing the engine via a user `@Bean` (because `axon-server-connector` on the classpath force-wins via ServiceLoader otherwise — see `2026-05-09 — Phase 9 / event-storage-engine: "auto-config wins" claim was WRONG`), so the entity registration silently goes with it. A clean framework fix would need a different gating signal — something like "JPA event-store entities are wanted" expressed as a property or marker bean — and that design choice is on the AF5 team, not us.
- Takeaway for the recipe / future migrations:
  - Whenever Phase 9 forces an explicit `@Bean EventStorageEngine` (which is whenever `axoniq-spring-boot-starter` is the starter — i.e. *always* on the commercial AF5 line), pair it with a project-wide `@EntityScan(basePackages = {"com.<app>", "org.axonframework", "io.axoniq.framework"})`. Don't trust `@RegisterDefaultEntities` to fire.
  - Note that adding `@EntityScan` *displaces* `AutoConfigurationPackages` for JPA entity discovery, so a partial scan (just one package) will break entities from autoconfigs that were silently filling the rest. Always scan the full set in one annotation.
  - The misleading "No ParameterResolver registered" message that JUnit 5 prints for `@SpringBootTest` constructor-injected tests really means "`SpringExtension` declined to claim the parameter because `@TestConstructor` mode is `ANNOTATED`". Either set `spring.test.constructor.autowire.mode=all` via `src/test/resources/spring.properties` (project-wide) or annotate the base class with `@TestConstructor(autowireMode = ALL)` (note: not inherited by subclasses).
- See: phase-9-follow-up commit (this commit); related commits `77d5ea3` (Phase 9 fix-up), `d3319d9` (the `@EntityScan` workaround), `ec5b2a8` (original "auto-config wins" claim that was wrong), `1228b5b` (the test refactor that reactivated `@SpringBootTest` and exposed all of this).

## 2026-05-12 — Phase 9 follow-up: AF5 async send breaks AF4 try/catch compensation; pooled tests need `@DirtiesContext`

- Context: `WhenCreatureRecruitedThenAddToArmyTest` and the two astrologer automation tests, after the `@MockitoSpyBean` → BPP-spy workaround (`0d22913`) made the spy assertions actually reach the verify stage.
- Surprises (three independent ones, exposed together):
  1. **Async compensation regression.** `WhenCreatureRecruitedThenAddToArmyProcessor` reacts to `CreatureRecruited` by first sending `AddCreatureToArmy` and, on failure (army full), compensating with `IncreaseAvailableCreatures`. Under AF4 the `send(...).getResultMessage()` line threw synchronously from a try-block, so the catch saw the `Can have max 7 …` violation and fired compensation. Under AF5 `CommandGateway.send(...)` returns a `CommandResult` whose `getResultMessage()` is a `CompletableFuture<? extends Message>` — the failure surfaces on the future, *never* in the try-block. The catch never runs; the test sees only the failing `AddCreatureToArmy` invocation on the spy and never the compensating `IncreaseAvailableCreatures`. This is a real behavioural regression in any AF4 automation that used try/catch around the gateway, not just a test-only issue.
  2. **Cross-method test contamination.** With `@SpringBootTest` and Testcontainers, three layers of state outlive a single `@Test`: the Postgres DB (one container per JVM), the Spring `ApplicationContext` (cached across all classes whose configuration hashes match — and ours all share `@Import({TestcontainersConfiguration, CommandGatewaySpyConfiguration})`), and the AF5 pooled-streaming processor tokens. The shared spy keeps accumulating invocations from earlier methods' events that are still flowing through the processor seconds later. `Mockito.reset(commandGateway)` in `@BeforeEach` is necessary but not sufficient — pooled processors keep dispatching after the reset.
  3. **`AggregateEventPublisher` cannot append twice to the same aggregate.** The utility lets `AggregateSequencer` allocate from `aggregate_sequence_number=0` under `AppendCondition.none()`. Two `publish(...)` calls for the same `aggregate_identifier` both write at sequence 0 → `uk7lm0ppm66bd86judy5vot9s42` unique-key violation.
